# 常见故障速查表

> 诊断时按这张表对号入座。每条给出：识别特征 → 首查命令 → 常见根因 → 处置。

## 1. 磁盘满

**特征**：`No space left on device`、`ENOSPC`、写文件失败
**首查**：`df -h`、`df -i`（inode 也要看）
**常见根因**：
- 日志暴涨（未轮转 / 应用刷日志）
- 已删除但被进程占用的文件（`lsof +L1`）
- inode 耗尽（小文件过多，`df -i` 100%）
- 容器镜像/层堆积

**处置**：
1. 定位：`du -xh --max-depth=1 / | sort -rh | head -20`
2. 清日志：`journalctl --vacuum-size=500M`；老日志压缩归档
3. 已删占用：`lsof +L1` 找到 PID 后重启该进程（**不要**直接 kill -9 生产进程）
4. inode：`find / -xdev -type f | sed 's|/[^/]*$||' | sort | uniq -c | sort -rn | head`

**警告**：磁盘满会导致数据库写失败、日志截断，优先处理。

---

## 2. OOM / 内存不足

**特征**：`Out of memory: Killed process`、`oom-killer`、`Cannot allocate memory`
**首查**：`dmesg -T | grep -i -E "oom|killed process"`、`free -h`
**常见根因**：
- 进程内存泄漏（RSS 单调增长）
- JVM/运行时堆设置超过物理内存
- 并发突增
- 容器未设 memory limit，被宿主 OOM

**处置**：
1. 找大户：`ps aux --sort=-%mem | head`
2. 临时缓解：systemd `MemoryMax=` 限流，或加 swap（仅缓解，不能根治）
3. 根治：修泄漏 / 调堆上限 / 扩容
4. **确认被杀的是不是关键进程**——OOM 杀谁由 oom_score 决定，可能杀掉数据库

---

## 3. 服务起不来

**特征**：`Failed to start`、`main process exited`、`status=1/203`
**首查**：`systemctl status <svc> -l --no-pager`、`journalctl -u <svc> -n 200`
**常见根因**：
- 配置语法错（nginx -t / apachectl configtest）
- 端口被占（`ss -lntp`）
- 依赖服务未起
- 文件权限/属主错
- 磁盘满导致无法写 pid/socket

**处置**：
1. 先看配置校验，**大部分服务起不来是配置错**
2. 查端口冲突
3. 查权限（`ls -l` 目标路径 + `ausearch -m avc` 看 SELinux）

---

## 4. SSH 连不上

**特征**：`Connection refused` / `Connection timed out` / `Permission denied (publickey)`
**分类排查**：
| 现象 | 大概率原因 | 首查 |
|---|---|---|
| refused（立即拒绝） | 服务没起 / 端口错 | 目标机 `ss -lntp \| grep 22` |
| timed out（无响应） | 防火墙丢包 / 主机挂了 / 网络不通 | `ping`、`traceroute`、`telnet host 22` |
| publickey denied | 密钥不对 / 权限过宽 | 目标机 `~/.ssh` 权限须 700，authorized_keys 600 |
| Too many auth failures | 客户端加载了过多密钥 | `ssh -o IdentitiesOnly=yes -i <key>` |

**警告**：timed out 且 ping 也通 → 多为防火墙 DROP，不是服务问题。

---

## 5. 数据库连接问题

**特征**：`Too many connections`、`connection pool exhausted`、`server has gone away`
**首查**：
- MySQL：`SHOW PROCESSLIST`、`SHOW VARIABLES LIKE 'max_connections'`
- PG：`SELECT count(*), state FROM pg_stat_activity GROUP BY state`

**常见根因**：连接泄漏（应用没归还）、连接池配置过小、慢查询占住连接、空闲连接不回收
**处置**：先确认是泄漏还是真并发，再决定调上限还是修代码。调 `max_connections` 要评估内存。

---

## 6. 性能退化

**先分清是 CPU / IO / 网络 / 锁**：
- `top` 看 us / sy / wa：wa 高是 IO 不是 CPU
- `iostat -x 1` 看 %util 与 await
- `pidstat -p ALL 1 5` 定位进程
- `ss -s` 看连接数

**注意**：load 高但 CPU 不高 → 多半是 IO 等待或 D 状态进程卡住（`ps aux | awk '$8 ~ /D/'`）。

---

## 7. 证书问题

**特征**：`certificate has expired`、`unable to get local issuer certificate`
**首查**：`openssl x509 -in cert.pem -noout -dates`、`openssl s_client -connect host:443`
**处置**：续签 → reload（不是 restart，避免中断）→ 确认自动续期 timer 有效

---

## 8. 时间漂移

**影响**：证书校验失败、日志顺序错乱、集群选主异常、分布式事务失败
**首查**：`timedatectl status`、`chronyc tracking`
**处置**：修 NTP 源可达性（内网常被防火墙拦 UDP 123）

---

## 9. inode 耗尽

**症状**：`df -h` 显示还有空间，但写入报 `No space left on device`。

**证据**：`df -i` 使用率接近 100%；大量小文件堆积（session、cache、临时文件、邮件队列）。

**措施**：
1. `df -i` 确认是 inode 而非容量问题
2. 找小文件多的目录：`find /var -xdev -type f | sed 's|/[^/]*$||' | sort | uniq -c | sort -rn | head`
3. 清理过期 session/cache/临时文件；必要时扩 inode（需重建文件系统，慎重）

**验收**：`df -i` 使用率降到 80% 以下。

## 10. 端口被占用 / 绑定失败

**症状**：服务起不来，日志报 `Address already in use` / `bind: Address already in use`。

**证据**：`net_status` 里该端口已有 LISTEN；`ss -lntp` 能看到占用进程。

**措施**：
1. 确认占用者：`ss -lntp | grep :<端口>` 或 `proc_list` 找进程
2. 若是残留进程（旧版本未退出）→ 停掉再起
3. 若是配置冲突（两个服务抢同一端口）→ 改配置
4. **不要**盲目 kill 陌生进程，先确认它是什么

**验收**：端口被目标服务持有，`net_status` 显示正确进程。

## 11. 连接被拒绝（Connection refused）

**症状**：客户端报 `Connection refused`。

**证据**：目标端口**没有** LISTEN（与「端口占用」相反——那个是有人占了，这个是没人听）。

**措施**：
1. `net_status` 确认该端口是否监听
2. 没监听 → 服务没起来 / 只监听了 127.0.0.1
3. 检查 `config_read` 里服务的 `bind` / `listen` 配置
4. 检查防火墙是否 DROP（DROP 表现为超时，REJECT 才是拒绝）

**验收**：客户端能建连。

## 12. 请求 / 连接超时

**症状**：客户端报 `timeout`，但服务端看似正常。

**证据**：连接数堆积、CLOSE_WAIT 多、后端响应慢。

**措施**：
1. 先分清是**连不上**（网络/防火墙）还是**连上了不响应**（后端卡住）
2. `net_status` 看 ESTABLISHED 是否堆积
3. 查后端：DB 慢查询、下游依赖超时、线程池耗尽
4. 防火墙 DROP 也表现为超时，用 `iptables -L -n -v` 看计数

**验收**：P99 延迟回到基线。

## 13. 文件描述符耗尽（too many open files）

**症状**：日志报 `Too many open files` / `EMFILE`。

**证据**：`proc_detail` 里 fdCount 接近 limits 的 `Max open files`。

**措施**：
1. 确认是**单进程**超限还是**系统级**超限
2. 单进程：查是否有连接/文件句柄泄漏（fd 只增不减）
3. 临时：调 `ulimit -n` 或 systemd `LimitNOFILE`
4. 根治：修泄漏点，别只调大上限

**验收**：fd 使用率稳定在 60% 以下且不持续增长。

## 14. 磁盘 IO 错误 / 坏道

**症状**：日志出现 `I/O error`、`Buffer I/O error`、`EXT4-fs error`、`medium error`。

**证据**：dmesg / journal 里的块设备错误；`smartctl -a` 的 Reallocated_Sector_Ct 增长。

**措施**：
1. **立即停止写入该盘**，避免扩大损坏
2. `dmesg | grep -i "i/o error"` 定位设备
3. `smartctl -a /dev/sdX` 看健康状态与重映射扇区
4. 有备份→换盘；无备份→先 ddrescue 抢救数据
5. 检查 RAID 状态是否已降级

**验收**：SMART 无新增错误，数据完整。

## 15. RAID 降级

**症状**：`/proc/mdstat` 出现 `[U_]` 或 `[U__]`，容量正常但无冗余。

**证据**：mdstat 里 degraded；dmesg 有 `removed` / `faulty`。

**措施**：
1. `cat /proc/mdstat` 确认哪块掉了
2. `smartctl` 检查故障盘是否真坏
3. 换盘后 `mdadm --add` 触发重建，**重建期间不要再压测**
4. 重建完成前，任何一块盘再坏 = 数据全丢

**验收**：`[UU]` 且 rebuild 完成。

## 16. DNS 解析失败

**症状**：`Could not resolve host` / `Temporary failure in name resolution`。

**证据**：`/etc/resolv.conf` 的 nameserver 不可达；`nsswitch.conf` 顺序异常。

**措施**：
1. 测解析：`getent hosts <域名>`（比 nslookup 更贴近实际调用链）
2. 检查 `config_read` 的 `/etc/resolv.conf` 与 `/etc/hosts`
3. 确认 nameserver 可达（`net_status` 看 53 端口）
4. 容器环境注意：容器内 resolv.conf 常被覆盖

**验收**：`getent hosts` 正常返回。

## 17. 日志暴涨

**症状**：磁盘被日志快速吃掉；单文件几分钟内涨几百 MB。

**证据**：同一消息模板高频重复；常见于上游重试风暴、健康检查失败循环、扫描攻击。

**措施**：
1. 按消息模板聚类（去掉时间/ID 后聚合），找重复度最高的那条
2. 重复度极高 → 几乎必然是循环重试或攻击
3. 先限流/降噪止血（调日志级别、加 rate limit），再看真实问题
4. 注意：本产品的 log-flood 规则只匹配明确的洪泛标记，不会把普通 ERROR 当暴涨

**验收**：日志增速回到正常水平。

## 18. 进程崩溃 / core dump

**症状**：日志出现 `segfault`、`core dumped`、`signal 11`。

**证据**：`coredumpctl list`（systemd）或内核日志。

**措施**：
1. 确认崩溃频率：偶发一次 vs 反复崩溃
2. 反复崩溃 → 看是否特定输入/特定时段触发
3. 保留 core 文件，交给开发分析栈
4. 临时缓解：supervisor 自动拉起，但要记录次数（反复拉起会掩盖问题）

**验收**：崩溃不再新增。

## 19. CPU 高负载 / 进程卡死

**症状**：load 很高，但 CPU 使用率不高；或单进程持续 100%。

**证据**：`sys_metrics` 的 loadPerCpu > 1；`proc_list` 里有 D 状态进程。

**措施**：
1. **先看 D 状态**：load 高而 CPU 空闲，几乎都是不可中断 IO（存储/挂载卡住）
2. D 状态 → 查存储链路（NFS 挂载丢失、磁盘故障、云盘限流）
3. CPU 真高 → `proc_list sortBy=cpu` 找元凶
4. 卡死进程要先看它在等什么，不要直接 kill -9（D 状态 kill 不掉）

**验收**：load 回到核数以下。

## 20. 慢查询 / 响应退化

**症状**：接口变慢，但没报错。

**证据**：DB 慢查询日志；连接池等待时间增长。

**措施**：
1. 先分清是 DB 慢、应用慢、还是网络慢
2. DB 慢 → 看慢查询日志、执行计划、索引是否失效
3. 应用慢 → 看 GC、线程池、下游依赖
4. 变更关联：`recent_changes` 看最近是否改过配置或发过版

**验收**：P99 回到变更前水平。

## 21. 疑似端口扫描 / 入侵探测

**症状**：短时间内大量连接不同端口；日志里大量 `Invalid user`、`connection reset`。

**证据**：`net_status` 的 SYN_RECV 异常；auth 日志里同一 IP 高频失败。

**措施**：
1. `net_status topRemote` 看连接数最高的对端
2. 结合 `sec_baseline` 检查暴露面（是否有本该内网的服务监听在 0.0.0.0）
3. 防火墙封禁来源，但**先确认不是自家扫描器**
4. 若伴随成功登录记录，按安全事件上报

**验收**：异常连接消失，且确认无成功入侵痕迹。

## 排查顺序原则

**先确认影响面，再定位根因**：
1. 影响多少用户/业务？（决定紧急度）
2. 是持续性还是瞬时？（持续 → 看累积证据；瞬时 → 看时间点前后）
3. 最近有没有变更？（有变更先怀疑变更，这是最高命中率的一条）

> 经验：生产故障里超过一半能追溯到最近一次变更。查不到根因时，先问"最近改了什么"。
