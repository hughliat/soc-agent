# 诊断操作手册（技能层）

> 这是"怎么干"的标准动作。专家层讲判断，这里讲步骤。

## 技能 1：从零开始诊断一台陌生机器

```
① diagnose_logs                     # 一步拿到候选问题清单
② 看 findings 的 severity 排序       # critical 先看
③ read_log 读关键日志上下文          # 确认不是断章取义
④ kb_lookup 查对应速查表             # 拿到标准处置流程
⑤ web_search 查不认识的报错          # 补充外部知识
⑥ 按固定格式输出结论                 # 见 AGENTS.md §三
```

**注意**：不要跳过 ②。一次报 20 条问题等于没报，按严重度取前 5 条。

## 技能 2：确认一个问题是不是"真问题"

日志里的 ERROR 不一定是要处理的问题。三个筛子：

1. **频次**：偶发 1 次 vs 持续每秒 → 后者才是问题
2. **时间**：是不是集中在某次变更后 → 是则优先怀疑变更
3. **影响**：有没有对应的业务失败 → 没有则可能只是噪声

三者都通过才升级为"要处理的问题"。

## 技能 3：给处置方案的正确姿势

分两段写，不要混：

```
【立即止血】（5 分钟内能做，先控制影响）
1. 具体命令
2. 预期效果
3. 风险提示（会不会中断服务）

【根治】（需要窗口期）
1. 根因修复动作
2. 验证方法
3. 防复发措施
```

**禁止**：只给"重启服务"。重启是止血不是根治，必须同时给出根因方向。

## 技能 4：判断"最近有没有变更"

这是最高命中率的排查方向（生产故障过半可追溯到变更）：

- `query_ansible` 查本机近期变更记录
- 查配置文件 mtime：`ls -lt --time-style=long-iso /etc/<svc>/`
- 查包安装时间：`rpm -qa --last | head` / `grep " install " /var/log/dpkg.log`
- 查服务重启时间：`systemctl show <svc> -p ActiveEnterTimestamp`

## 技能 5：日志时间对齐

多个来源的日志时间不一致会让关联分析全错。先确认：

```bash
timedatectl status          # 系统时区与同步状态
date -u                     # UTC 时间
journalctl --utc            # 统一用 UTC 看
```

**坑**：应用日志用本地时间、系统日志用 UTC、容器日志用宿主时间 —— 三者混着看必然错位。

## 技能 6：写诊断报告

结构固定，不要自由发挥：

1. 一句话结论
2. 问题清单（按严重度，每条带证据+根因+措施+验收）
3. 未覆盖的维度（诚实说明哪些没查）
4. 建议的后续动作

**长度控制**：5 条以内讲透，比 20 条罗列有用。

## 技能 7：按现象选对工具（24 个工具的选择表）

工具多不等于乱用。**先按现象定方向，再调工具**，比"全部扫一遍"既快又省。

| 现象 | 首选工具 | 为什么 |
|---|---|---|
| "服务器有问题""卡" | `sys_metrics` | 先看负载/内存/磁盘是否饱和，一步定性 |
| 某个服务起不来 | `diagnose_logs` → `journal_query` | 规则库先给候选；journal 看 systemd 视角的启动失败原因 |
| 磁盘满了 / 写不进去 | `sys_metrics` | 同时看容量与 inode——`df -h` 看不出 inode 耗尽 |
| "昨天还好好的" | `recent_changes` | 变更是最强线索，先查最近改了什么 |
| 接口慢 / 超时 | `net_status` + `proc_list` | 先分清连接层堆积还是进程层饱和 |
| 进程吃内存/fd 涨 | `proc_detail` | 单进程的 fd 用量、limits、cgroup 一次看全 |
| 连接数异常 | `net_status` | CLOSE_WAIT 高=程序没 close；SYN_RECV 堆积=扫描或半开连接 |
| 怀疑被入侵 | `sec_baseline` → `net_status` | 先看暴露面（谁在 0.0.0.0 上听），再看异常连接来源 |
| 改配置前想确认现状 | `config_read` | 只给生效行，跳过注释噪声 |
| 文件被改过没有 | `file_hash` | mtime 可伪造，sha256 不会 |
| 升级后出问题 | `pkg_history` | 最近的包变更记录 |
| TLS 握手失败 | `cert_check` | 证书过期是最常见原因，30 天内会预警 |
| 服务清单与自启 | `svc_status` | 看"配置为开机启用"，运行态要配 `journal_query` |
| 历史同类问题 | `kb_lookup` | 先查本机记忆与速查，别重复排查 |
| 生僻报错看不懂 | `web_search` | 只发查询词，不发日志原文 |

### 三条使用纪律

1. **不要一上来就 diagnose_logs 全扫**。它扫的是文件日志，覆盖不到资源饱和、进程卡死、端口占用——这些得靠 `sys_metrics` / `proc_list` / `net_status`。

2. **`journal_query` 是唯一子进程工具**，也是唯一能看到 systemd 视角的工具。文件日志里没有的启动失败原因，往往在 journal 里。但它只在 Linux 有。

3. **读不到就说读不到**。工具有 `available: false` 时，如实告知"该维度本机取不到"，不要用推测填补。运维宁可知道盲区在哪，也不要一个看着完整的错误答案。

### 平台差异（回答前必须先确认）

`journal_query` / `proc_list` / `proc_detail` / `net_status` / `svc_status` / `pkg_history`
六个工具依赖 Linux 的 `/proc` 与 systemd。**macOS 上它们会明确返回"本平台不适用"**——
这不是故障，是平台限制。回答时应说明"该维度不可得"，而不是让用户以为机器没问题。
