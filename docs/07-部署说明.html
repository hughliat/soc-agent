小安 soc-agent · 部署说明

版本 1.1.0 ｜ 适用平台 麒麟 / 主流 Linux ｜ 部署形态 终端交互 + 定时巡检

一、产品概述

小安（soc-agent）是部署在服务器上的本机故障诊断智能体。运维用一句话描述现象，它自行读取本机日志、匹配内置故障规则、必要时联网核对报错含义，输出问题清单 + 根因 + 处置措施 + 验收方法。

核心定位：只诊断，不执行 产品没有任何命令执行能力。不改配置、不重启服务、不写业务文件。所有处置动作由人执行。 这不是"暂时没做"，是设计前提——它决定了本产品的等保定级与审计口径。

能力边界

可以做明确不做
· 读本机日志（含轮转与 gzip）
· 匹配 21 类内置故障模式
· 查 systemd journal（按服务/时间/级别）
· 采集资源指标、进程、网络、服务状态
· 检查安全基线（口令/SSH/sudo/暴露面/SUID）
· 读白名单内的配置文件
· 查最近变更与包变更史
· 联网核对报错含义（只发查询词，不发日志原文）
· 把诊断报告发邮件
· 定时巡检，有故障告警、无故障日报 		· 执行任何命令（含 bash / shell）
· 修改配置、重启服务、杀进程
· 写业务文件、上传下载文件
· 派生子代理、安装插件、连接 MCP
· 发送任意内容到任意邮箱
· 回答与本机运维无关的问题

二、环境要求

它不是独立程序 —— 必须先装 dsh 本产品是 dsh 的插件，界面层用的是 dsh-tui。依赖顺序不可颠倒： 
Node.js ≥ 18   →   dsh CLI   →   dsh-tui 界面   →   soc-agent（本产品）
（用户自装）      （用户自装）    （install.sh 会装/打补丁）   （本安装包）
install.sh 会先检查 dsh 是否存在，缺失时直接报错并给出三种安装方式， 不会让你装到一半才发现跑不起来。

软件依赖

组件要求说明
操作系统麒麟 V10 / 主流 Linuxglibc ≥ 2.17；macOS 可用但部分能力受限
Node.js≥ 18（推荐 20 LTS）启动自检会拦住低版本
dsh 运行时已安装 dsh CLI插件挂在 dsh profile 中运行
基础命令tar gzip grep find均为系统自带

三、安装

先装运行环境，再装本包 —— 顺序不能反 本产品是 dsh 的插件，界面层是 dsh-tui。 拿到本包却只解压执行，是跑不起来的。完整依赖链： 
第1步  装 Node.js（≥18）        —— 本产品的运行时
第2步  装 dsh                    —— 插件宿主
第3步  装 dsh-tui                —— 终端交互界面
第4步  装 soc-agent（本包）       —— 诊断智能体
第5步  配置模型端点 + 自检启动
下面按 麒麟 / Linux / Windows 三平台分别给出 1~5 步的完整命令。

3.1 麒麟（Kylin，信创服务器）

装 Node.js ≥ 18（不要用系统源，版本常低于 18） 
# 下载官方 Linux x64 包（在有网机器或提前拷入）
curl -O https://nodejs.org/dist/v20.18.0/node-v20.18.0-linux-x64.tar.xz
tar -xJf node-v20.18.0-linux-x64.tar.xz -C /opt
echo 'export PATH="/opt/node-v20.18.0-linux-x64/bin:$PATH"' >> /etc/profile.d/node.sh
source /etc/profile.d/node.sh
node -v          # 应输出 v20.x
装 dsh（插件宿主） 
# 有外网
npm i -g @deepseek-ai/dsh

# 内网：从同平台联网机器拷全局包
#   源机：  tar -czf dsh-global.tgz -C "$(npm root -g)" @deepseek-ai
#   目标机：tar -xzf dsh-global.tgz -C "$(npm root -g)"

dsh --version    # 验证
装 dsh-tui 并初始化 profile 
dsh --profile dsh-tui   # 首次运行会自举并拉取 dsh-tui 界面层

# 若自举没装好界面层（内网常见），显式安装：
dsh plugin --profile dsh-tui add @deepseek-harness-tui/dsh-tui
# 内网无外网时，dsh-tui 的依赖树在「十、离线部署」的离线包里

# 退出 dsh（按 /exit），继续下一步
装 soc-agent（本包）到 profile 目录 
sha256sum -c soc-agent-1.1.0.tar.gz.sha256
tar -xzf soc-agent-1.1.0.tar.gz
cd soc-agent-1.1.0
./install.sh dsh-tui        # 拷到 ~/.dsh/profiles/dsh-tui/node_modules/soc-agent
配模型端点 + 自检启动 
export SOC_LLM_BASE_URL="http://<内网模型地址>/v1"
export SOC_LLM_API_KEY=""
export PATH="$HOME/.dsh/profiles/dsh-tui/node_modules/soc-agent/bin:$PATH"
soc --check      # 自检，全绿才往下
soc              # 进入交互界面
麒麟两处特有注意 ① /bin/sh 是 dash，本产品脚本已全部按 dash 兼容编写（验收脚本有专项检查）。 ② systemd 用户级 timer 默认「登录才跑」，服务器要 sudo loginctl enable-linger <用户>。

3.2 主流 Linux（CentOS / Ubuntu / Debian / openEuler 等）

步骤与麒麟完全一致，仅 Node 安装方式可选系统包（版本足够时）：

# Ubuntu / Debian
curl -fsSL https://deb.nodesource.com/setup_20.x | bash - && apt install -y nodejs

# CentOS / RHEL 系（含 openEuler）
dnf module install -y nodejs:20    # 或 dnf install -y nodejs

其余四步（装 dsh → 装 dsh-tui → 装 soc-agent → 配模型自检）与 3.1 完全相同，不再重复。注意装完 Node 先 node -v 确认 ≥ 18。

Windows 仅用于开发与体验，不作为生产部署 六个诊断工具（journal_query / proc_list / proc_detail / net_status / svc_status / pkg_history）依赖 Linux 的 /proc 与 systemd，在 Windows 上不可用。 生产巡检请在麒麟 / Linux 上部署。以下步骤供本机体验与测试。
装 Node.js ≥ 18

从 nodejs.org 下载 Windows 安装包（.msi），一路下一步，勾选「Add to PATH」。装完新开 PowerShell 验证 node -v。

装 dsh 
npm i -g @deepseek-ai/dsh
dsh --version
装 dsh-tui 并初始化 
dsh --profile dsh-tui
# 或：dsh plugin --profile dsh-tui add @deepseek-harness-tui/dsh-tui
解压并安装 soc-agent 
# 用 7-Zip 或 tar 解压（Win10+ 自带 tar）
tar -xzf soc-agent-1.1.0.tar.gz
cd soc-agent-1.1.0
sh install.sh dsh-tui      # 若提示缺 sh，用 Git Bash 执行
配模型 + 启动 
# PowerShell
$env:SOC_LLM_BASE_URL="http://<模型地址>/v1"
$env:SOC_LLM_API_KEY=""
soc

四、配置

4.1 模型端点

环境变量必填说明
SOC_LLM_BASE_URL建议内网 OpenAI 兼容端点。不填则用运行时默认（可能指向公网，不合规）
SOC_LLM_API_KEY是端点密钥。回退顺序：本项 → DEEPSEEK_API_KEY

4.2 邮件（报告外发）

不配置也能用产品，只是发不出邮件（诊断、巡检照常）。

环境变量必填说明
SOC_SMTP_HOST发信必填SMTP 服务器地址
SOC_SMTP_PORT否默认 465（直连 TLS）/ 587（STARTTLS）
SOC_SMTP_SECURE否0 表示不用 TLS。默认启用
SOC_SMTP_USER / SOC_SMTP_PASS视网关AUTH LOGIN 认证
SOC_SMTP_FROM发信必填发件人地址
SOC_MAIL_ALLOWLIST发信必填收件人白名单，逗号分隔。不配 = 全部拒绝
SOC_SMTP_INSECURE否1 跳过证书校验（内网自签证书场景，会降低安全性）
白名单是硬门槛，不是可选项 智能体只能发给白名单内的地址；未配置时发送请求被直接拒绝。 这是防止产品变成"任意外发通道"的关键设计。 定时巡检的收件人还需与 patrol.json 的 recipients 同时匹配。

4.3 定时巡检

sh ~/.dsh/profiles/dsh-tui/node_modules/soc-agent/bin/install-timer.sh

首次执行会生成配置与模板：

  • ~/.dsh/soc-agent/config/patrol.json —— 收件人、阈值、扫描范围
  • ~/.dsh/soc-agent/config/templates/daily.md.tpl —— 日报模板
  • ~/.dsh/soc-agent/config/templates/alert.md.tpl —— 告警模板
任务频率行为
soc-patrol-alert每 30 分钟只在命中故障时发信；健康时静默
soc-patrol-daily每天 08:00无论有无故障都发日报
soc-logmanage每周日 03:30压缩大日志（只压不删，可 gunzip 还原）

改频率：SOC_ALERT_MINUTES=15 SOC_DAILY_AT=07:30 sh install-timer.sh

systemd 用户级 timer 默认「登录才跑」 服务器场景需要未登录也执行：sudo loginctl enable-linger <用户>。 不做这一步巡检会静默停止——启动自检会检测 linger 状态并提示。

4.4 patrol.json 字段

{
  "recipients": ["ops@example.com"],
  "severityThreshold": "high",
  "scan": { "sinceHours": 24, "maxFiles": 15, "linesPerFile": 300 },
  "sendDailyEvenIfHealthy": true,
  "templates": { "alert": "alert.md.tpl", "daily": "daily.md.tpl" }
}
字段说明
recipients固定收件人。留空则不发送（日志会明确报「未配置收件人」，不是静默失败）
severityThreshold什么级别算故障：critical 最严 / high 默认 / medium 最敏感
scan.sinceHours只看最近多少小时的日志
scan.maxFiles最多扫几个日志文件（按 mtime 倒序）
sendDailyEvenIfHealthyfalse 则健康时连日报也不发

4.5 日报模板占位符

模板为纯文本，只做单层替换，不支持表达式（无注入面）。改完下次巡检立即生效，无需重启。

占位符内容
{{hostname}}主机名
{{date}} / {{time}}日期 / 完整时间
{{summary}}一句话总评（确定性生成，不经过模型）
{{findings}}问题清单（每条含证据、措施、验收）
{{topLabel}} / {{topSeverity}}最严重那条的名称 / 级别
{{scanned}}扫描范围（几个日志 / 几行）
{{sinceHours}}覆盖时段
{{healthyLine}}健康时的一句说明（有故障时为空）

5.2 采集脚本：补齐它拿不到的证据

智能体不能执行命令。服务运行态、SMART、部分系统指标需要命令才能拿到，用采集脚本一次跑完把输出贴回：

sh ~/.dsh/profiles/dsh-tui/node_modules/soc-agent/bin/collect.sh > evidence.txt

输出带 === SECTION: xxx === 分段（主机 / CPU / 内存 / 磁盘 / 服务 / 端口 / 最近变更 / 日志 / 安全基线 / 时间），约 22 段、200 行。纯只读，不写任何文件。

某段显示 [skipped] 表示该维度本机取不到，模型会按「未覆盖」处理，不会臆测。

5.3 发报告

直接说「把这份诊断发邮件给 ops@example.com」，前提是该地址在白名单内。

5.4 可用命令

命令用途

/model切换模型（内网多端点时用）
/lang / /theme切换界面语言 / 主题

共 8 个。其余命令（含 /context、/plugins、/mcp、/hooks、/provider、/update、/workspace 等）已从命令表移除。

六、能力参考

6.1 工具清单（25 个，24 只读 + 1 记忆沉淀）

其中 23 个由本产品实现，另 2 个（web_search / web_fetch）为框架自带、仅供联网核对报错含义。模型可见的工具就是这 24 个，不多不少。

级别模式
critical磁盘空间耗尽 · inode 耗尽 · 内存不足/OOM · 磁盘 IO 错误/坏道 · RAID 降级
high服务启动失败 · 端口被占用 · 连接被拒绝 · 请求超时 · 文件描述符耗尽 · 证书过期 · 进程崩溃(core dump) · 数据库连接失败/连接池耗尽 · CPU 高负载/进程卡死 · 疑似端口扫描

七、安全设计

7.1 四层防线

层机制作用
1（主）工具白名单 restrict({allow})模型可见工具收敛为 25 个
2执行守卫 guard()兜住白名单管不到的框架自带工具（实测拦下 subagent）
3沙箱锁死read-only + 审批 never；权限表只留 soc-readonly，界面里选不到完全访问
4插件禁用bash / pwsh / fs / subagent / workflow / plugin-manager / mcp 不加载

7.2 界面封禁清单

位置封禁内容
启动页会话与工作区、设置、有新版本、后台任务、投喂 Star —— 全部摘掉，只留模型与思考深度
底部参数行不渲染 preset / permission 两个值
命令表63 → 8 个。/context（会摊开系统提示词）、/plugins、/mcp、/hooks、/provider 等移除
权限档位只剩 soc-readonly；workspace-write / danger-full-access 从预设表删除
Agent 预设钉死 standard，切换被 config 优先级挡住
更新检查不联网查版本（checkForTuiUpdate 直接返回空）

7.3 审计

每次工具调用落一条审计（~/.dsh/soc-agent/audit/，按天分文件）：谁、何时、调了哪个工具、传了什么参数、返回了什么。定时巡检也留痕（patrol-alert / patrol-daily）。

八、运维

8.1 启动自检（8 项）

检查项级别不通过说明
Node ≥ 18阻断运行时版本过低
profile 与插件已安装阻断没装或装错 profile
权限表已锁死（仅 soc-readonly）阻断配置被改过
沙箱模式 = read-only阻断沙箱被放开
dsh-tui 封禁补丁完好 + 命令数 = 8阻断界面入口被还原（通常是升级后没重打补丁）
审计目录可写阻断审计落不了盘
模型 API Key阻断没配跑不起来
定时巡检是否在跑（含 linger）警告未安装或未开 linger，巡检会静默停止

应急跳过：soc --skip-check（需输入 yes 二次确认，仅排障时用）。

8.2 升级

升级会冲掉界面封禁补丁 dsh-tui 一升级，被封禁的文件被整体替换，封禁静默失效——不报错，只是界面恢复原样。 所以升级必须走脚本，不要手工 pnpm add。 
sh tools/upgrade.sh --check      # 只看当前版本
sh tools/upgrade.sh 0.14.0       # 升级到指定版本
sh tools/upgrade.sh              # 升到 latest

脚本四步：备份 profile → 升级 → 强制重打补丁 → 四项验证（命令数、补丁标记、单测）。任一不过即告警并给回滚命令。

任何手工动过 node_modules 之后，务必执行：sh tools/patch-dsh-tui.sh --check

8.3 日志压缩

node bin/logmanage.js --dry-run            # 只看会压什么
node bin/logmanage.js                      # 压自己的日志
node bin/logmanage.js --include-system     # 连 /var/log 一起压（慎用）

只压缩不删除（gzip，可 gunzip 还原）；不动正在写入的文件；默认只管自己的日志目录——/var/log 归 logrotate 管，重复轮转会打乱既有规范。

九、故障排查

启动报「自检未通过」

按每项后面的「修复：」提示操作。最常见的两条：

  • 封禁补丁缺失 → sh tools/patch-dsh-tui.sh
  • 权限锁死缺失 → 重跑 ./install.sh dsh-tui（会自动补齐）

发邮件报「未配置收件人白名单」

设 SOC_MAIL_ALLOWLIST。这是有意的安全默认，不是故障。

定时巡检没有任何邮件

  1. sh bin/install-timer.sh --status 看是否已安装
  2. systemd 场景确认 loginctl show-user $(id -u) -p Linger 为 yes
  3. 看 ~/.dsh/soc-agent/logs/alert.log 与 daily.log
  4. 手工试跑：node bin/patrol.js --mode daily

日志读不到

把运行用户加入日志组：sudo usermod -aG adm <用户>（Debian 系）或 wheel（RHEL/麒麟）。重新登录生效。读不到的后果是诊断能力受限，不会报错——自检里显示为警告。

某工具返回「本平台不适用」

journal_query / proc_list / proc_detail / net_status / svc_status / pkg_history 依赖 Linux 的 /proc 与 systemd，在 macOS 上不可用。这是平台限制，不是缺陷。

界面显示英文

用 /lang 切换（该命令在白名单内）。

十、离线部署（生产内网必读）

离线包与平台强绑定，不能跨平台搬运 依赖树里含原生二进制（@img/sharp-<platform>、libvips 的 .so）。 在 macOS 上生成的包，拷到 Linux 一定装不上。 必须在与目标环境相同的操作系统 + 架构上生成。

10.1 为什么需要离线包

在线安装走 dsh plugin add，它需要访问 npm registry 拉依赖树（约 86 MB、上百个包）。生产内网通常没有外网出口，这条路径走不通。

离线包把整棵依赖树随包带上，安装时直接铺到 profile 目录，跳过包管理器。

10.2 三个层次，按需选择

包体积何时需要
基础包soc-agent-<ver>.tar.gz 约 1 MB 目标机已装 dsh 且可访问 npm 源
离线包soc-agent-<ver>-offline-<os>-<arch>.tar.gz 约 25–90 MB 目标机已装 dsh，但不能访问 npm 源（内网常态）
dsh 本体全局包 约 500 MB 目标机连 dsh 都没装（全新内网机器）

10.3 生成离线包

在一台与目标环境同平台、且能联网的机器上（比如测试环境）：

# 1) 先完成一次在线安装（把依赖树拉到本机）
./install.sh dsh-tui

# 2) 检查平台相关依赖（确认包只能用于本平台）
sh tools/make-offline.sh --check

# 3) 生成离线包
sh tools/make-offline.sh
# 产物：dist/offline/soc-agent-<ver>-offline-<os>-<arch>.tar.gz（含 sha256）

10.4 目标机离线安装

# 校验
sha256sum -c soc-agent-1.1.0-offline-linux-x86_64.tar.gz.sha256

# 解压安装（脚本会自动校验平台匹配）
tar -xzf soc-agent-1.1.0-offline-linux-x86_64.tar.gz
cd soc-agent-1.1.0-offline-linux-x86_64
./install-offline.sh                  # 装到默认 profile dsh-tui
./install-offline.sh <profile>        # 或指定 profile

离线安装脚本做七件事：检查 node/dsh → 校验平台匹配（不匹配直接拒绝）→ 备份旧 node_modules → 铺依赖树 → 装插件 → 重打界面封禁补丁 → 跑启动自检。

10.5 目标机没有 dsh 怎么办

离线包只含插件依赖，不含 dsh 本体（500 MB，且含原生模块，同样平台绑定）。从同平台的联网机器拷全局包：

# 源机（联网、与目标同平台）
tar -czf dsh-global.tgz -C "$(npm root -g)" @deepseek-ai

# 目标机
tar -xzf dsh-global.tgz -C "$(npm root -g)"
# 确认可用
dsh --version
Node 也要预装 dsh 与本产品都依赖 Node ≥ 18。内网机器通常没有 Node， 需要从同平台下载 Node 官方压缩包（node-v20.x-linux-x64.tar.xz）一并带入。 不要用系统包管理器装 Node——麒麟自带源里的 Node 版本往往低于 18。

10.6 离线部署检查清单
