这份文档给接手的人看：模块怎么切、工具怎么注册、八个关键决策当时踩了什么坑、 哪些地方看着奇怪但其实是对的、还有哪些坑没填。

01技术栈与选型

选择是什么为什么不是别的
Node ≥ 18，dependencies: {}运行时零第三方依赖内网离线部署，依赖树越大越难搬；且 dsh 本身依赖 Node，Node 一定存在
宿主插件（非独立进程）通过 apply(ctx) 注入 tools / agents / systemPrompt工具面收敛、提示词注入、审计钩子都必须发生在宿主的生命周期里，独立进程做不到
插件 ESM + 核心 CJSlib/index.js 是 ESM；src/core/* 是 CommonJS插件入口由宿主以 ESM 加载；核心逻辑要能被单测与 CLI 用 require 直接调用
补丁器用 Node 而非 pythontools/patcher.mjs麒麟最小化安装不保证有 python3；缺了会让界面封禁静默失效
规则先算，模型后解释src/core/diagnose.js 纯函数同一份日志任何人跑都得到同一批 findings；模型只能引用，不能编

切分原则只有一条：核心逻辑不认识模型、不持有权限。所以 src/core/* 全是可单测的纯函数， 权限与审计全部压在 lib/index.js 这一个文件里——安全只有一个收敛点，review 时不用满仓库找。

03工具注册契约

每个工具是一个对象，四个字段缺一不可：name / description / parameters / output / execute。

ctx.tools.register({
  name: 'read_log',
  description: '读取指定日志文件的片段…路径必须来自 ls_logs 的结果。只读。',
  parameters: {
    type: 'object',
    additionalProperties: false,          // 硬约束：模型不能塞未声明参数
    required: ['path'],
    properties: {
      path:  { type: 'string',  description: '日志文件绝对路径（来自 ls_logs）' },
      lines: { type: 'number',  description: '读最后多少行，默认 200、最大 2000' },
      grep:  { type: 'string',  description: '只保留包含该关键字的行' },
    },
  },
  output: {
    schema: {
      type: 'object',
      additionalProperties: false,        // 输出多一个未声明字段 = 模型侧"工具坏了"
      required: ['path', 'lines', 'truncated'],
      properties: { path: {...}, lines: {...}, truncated: {...}, note: {...} },
    },
    render(args, value) {               // 结构化结果 → 人可读的几行文本
      return [{ type: 'text', text: `${value.path}（返回 ${value.lines.length} 行）\n` + value.lines.join('\n') }];
    },
  },
  async execute(args) {
    return runQuery('read_log', args, (a) => { /* 真实逻辑 + 读日志 */ });
  },
});

四条硬约束

  1. parameters 必须是标准 JSON Schema。运行时不编译，直接原样发给模型；用框架 DSL 形状会报 type: null。
  2. additionalProperties: false 是双刃剑。它能挡住模型乱塞参数，也会把"我们想给模型的额外字段"判非法——见 D4。
  3. 所有执行都过 runQuery()。它统一做两件事：写审计、把 refs 从返回值里剔除。
  4. 失败要能说明原因。取不到数据时返回 { available: false, reason }，而不是空数组——空数组会被模型当成"没问题"。

04八个关键决策

D1 · 白名单必须打在 agent scope 上

现象：白名单写了，但模型仍然看得见 19 个工具（含 bash、写文件、子代理）。
根因：ctx.tools.restrict() 强制要求 agent scope，插件 apply 的 ctx 是 plain context， 调用必然抛错；外层 try/catch 把错误吞了，于是 restrict 从未生效，而且没有任何报错。
修法：监听 agent/created 取 agent.ctx 再 restrict；再用 queueMicrotask 回填"插件加载晚于 agent 创建"的情况。 

const onAgentCreated = (payload) => {
  const agent = payload?.agent;
  const agentCtx = agent?.ctx;                  // ← 必须是 agent 的 ctx
  if (!agentCtx?.tools) return;
  const disposer = agentCtx.tools.restrict({ allow: ALLOWED_TOOLS });
  restrictDisposers.add(disposer);
};
ctx.on?.('agent/created', onAgentCreated);
queueMicrotask(backfillExistingAgents);         // 事件已错过的兜底

验证方式：探针 dump agent scope 的工具面。修复前 19 个，修复后精确等于 ALLOWED_TOOLS 的 25 个。

D2 · restrict 管不到 own-layer，所以还要 guard

restrict 按设计只过滤继承层（global + 祖先层），不动 scope 自己注册的工具。 dsh-tui 的 preset 会往 agent 自己层注册 subagent，所以 TUI 下模型可见 12 个（多一个）。
修法：在 plain context 上注册 ctx.tools.guard()，单调、不可推翻，对所有工具调用生效。 实测拒绝信息：soc-agent 只读策略：禁止调用工具「subagent」。

两层不是冗余 restrict 管"看得见"，guard 管"调得动"。缺 restrict，工具面爆炸；缺 guard，own-layer 有缺口。两个都要。

D3 · 参数用标准 JSON Schema，别用 DSL

register() 不编译 parameters，直接原样发给模型。用框架 DSL 形状会得到 type: null，模型侧表现为"工具没有参数"。

D4 · refs 必须剔除后再返回

审计要记"这次读了哪些证据"，所以工具内部会在返回值里塞 refs。 但 output.schema 是 additionalProperties: false，多一个未声明字段就会被判输出非法—— 模型侧表现为"工具坏了"，整条诊断链失效（实测报 value.refs is not a declared property）。
修法：runQuery() 统一解构剔除，审计拿得到、模型看不到。 

if (result && typeof result === 'object' && 'refs' in result) {
  const { refs: _dropped, ...rest } = result;   // 审计已写，模型不该看到
  return rest;
}

D5 · 知识库路径不能用 import.meta.url

dsh 的 loader 会把插件挂到 profile 的虚拟 URL（…/profiles/<name>/#soc-agent）， new URL('../knowledge/', import.meta.url) 算出来指向 profile，知识库直接找不到。
修法：用 require.resolve('../package.json') 拿自己包的真实位置，再拼 knowledge/。

D6 · 稳定序列化：v1 有漏洞，v2 才拦得住篡改

审计哈希原先用 JSON.stringify(obj, Object.keys(obj).sort())。那个"键名数组"是 replacer， 对所有层级生效：嵌套对象里不在顶层键名集合中的字段会被整体丢弃。
后果很实在：篡改 toolCalls 里的工具参数、referencedEventIds、模型输出，hash 完全不变，审计链形同虚设。 

// v2：递归排序的全量序列化，任何字段改动都会改变 hash
function stableStringify(v) {
  if (v === null || typeof v !== 'object') return JSON.stringify(v);
  if (Array.isArray(v)) return '[' + v.map(stableStringify).join(',') + ']';
  const keys = Object.keys(v).sort();
  return '{' + keys.map((k) => JSON.stringify(k) + ':' + stableStringify(v[k])).join(',') + '}';
}

每条记录带 alg（v1 / v2），verify() 按记录自身版本重算： 旧记录用旧算法校验，历史链不会因算法升级集体"被篡改"。审计链一旦报假警，就再也没人信它。

D7 · 审计写失败不能静默吞掉

"全程逐条可审计"是核心承诺。写审计失败时：查询结果照常返回（不阻断诊断），但必须 ctx.logger.warn() 明确告警——不能既不写也不说。

D8 · 补丁器必须幂等且"逐项补缺"

早期的界面补丁脚本用"标记存在就跳过"。结果：后来新增的替换项永远不生效，而且看起来一切正常。 现在的规则是逐项检查补缺：每个锚点单独判定，能做就做，做不了报错非零退出。 同时每次改动先备份 *.soc-agent-backup，改完 node --check 校验语法，语法错自动回滚该文件。

补丁器要主动探测所有 dsh-tui 副本 dsh 实际加载的是 ~/.dsh/profiles/*/node_modules/ 里那份，不是全局 nvm 那份。 只改全局等于没改——这个坑踩过，所以脚本会扫所有副本。

05数据模型

事件（model.js）

字段取值说明
idevt-<ms>-<seq>单进程内单调，不依赖随机，便于审计按 ID 排序
srcansible / tianqing / onesec / custom来源白名单，非法值降级
whenepoch ms时区无关，展示时才本地化
where / what字符串必填，缺失直接拒绝建事件
resultok / changed / failed / unreachable / alert / info / skip枚举，非法降级
severityinfo / low / medium / high / critical有序，可比较

幂等

dedupKey = f(src, where, when)：同一份日志重跑不产生重复事件；对位置（路径/行）敏感， 所以同一时刻不同位置的事件不会被误合并。

审计记录

{ ts, question, toolCalls: [{ tool, args, eventIds, at }],
  referencedEventIds, note, prevHash, alg, hash }

06故障规则库

21 条规则，(src/core/diagnose.js)。加一条故障类型 = 加一个 RULES 条目，不改逻辑。

{
  key: 'disk-full',
  label: '磁盘空间耗尽',
  severity: 'critical',
  category: 'storage',
  re: /no space left on device|disk quota exceeded|ENOSPC/i,   // 单行正则
  remedy: [ 'df -h / df -i …', 'du 逐层定位 …', 'lsof +L1 查已删除未释放 …' ],
  verify: 'df -h 目标分区回落到 85% 以下，且业务写入恢复',       // 修完怎么确认
}
级别规则
critical磁盘空间耗尽 · inode 耗尽 · 内存不足/OOM · 磁盘 IO 错误/坏道 · RAID 降级
high服务启动失败 · 端口被占用 · 连接被拒 · 请求超时 · fd 耗尽 · 证书过期 · core dump · 数据库连接失败 · CPU 高负载 · 疑似端口扫描
medium认证失败/疑似爆破 · 权限不足 · DNS 解析失败 · 日志暴涨 · 时间漂移 · 慢查询

规则命中给的是候选诊断，不是最终结论。模型可以结合联网资料补充或推翻，但必须引用 finding 的证据。 合并逻辑：不同文件命中同一 key 时合并计数并保留最多 5 条样本，排序按"级别 → 次数"。

07日志发现与读取的边界

这是"只读"能否成立的关键模块（logdiscover.js）：

  • 白名单根目录：只扫约定的日志目录，extraRoots 也必须是日志类目录。
  • 敏感路径拦截：命中敏感路径规则直接跳过（不返回给模型）。
  • 读必须可溯源：read_log 会重新跑一次发现，把传入路径与清单比对，不在清单内一律拒绝—— 这是防任意文件读取的强制约束，不是建议。
  • 大文件不整读：只读尾部 N 行（默认 200、上限 2000），支持 gzip 轮转文件。

08巡检与邮件

bin/patrol.js 复用同一套规则与模板，不经过模型：定时任务不该依赖模型可用性。

  • 配置与模板首次运行自动生成：patrol.json + daily.md.tpl + alert.md.tpl。
  • 模板只做单层占位符替换（{{hostname}} 等），不支持表达式——没有注入面。
  • 邮件双门槛：SOC_MAIL_ALLOWLIST（不配 = 全拒）+ patrol.json 的 recipients。
  • 日志压缩只压不删，默认只管自己的日志目录（/var/log 归 logrotate）。

#问题说明与建议
1单测夹具缺失7 条 Ansible 用例读 ../dsh-ansible-logs/fixtures/*，该目录未随包发布；交付包内 node tests/run.js 不会全绿。建议把夹具收进 tests/fixtures/ 或缺失时显式 SKIP。
2Windows 下无法直接跑全量单测以文件路径 import 插件时触发 ERR_UNSUPPORTED_ESM_URL_SCHEME。Windows 仅供开发体验，生产在 Linux。
3工具数口径曾有三处不一致旧版 package.json 写 24、dsh.plugin.json 写 22、文档写 25。现统一为 25（23 自有 + 2 框架），以 ALLOWED_TOOLS 为准。
4知识库层数说法不一README 称"7 库"，实际目录是 5 层（纪律/专家/技能/知识/记忆）。以 kb_lookup 的 layer 枚举为准。
5天擎 / OneSEC 适配器未验真标 verified: false，无真实样本；接入前需用真实导出校准字段。
6大日志未压测10 万行场景的性能与准确率未验证，目前靠行数上限兜底。
7DB 只读连接器未接驱动SELECT-only 拦截已就位，未连真库验证。
8插件层无自动化测试restrict / guard 的验证依赖宿主环境探针，回归靠手工。soc --check 只能间接兜住"补丁被打回原形"。
