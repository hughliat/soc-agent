总体方案

一个不许动手的智能体，怎么把运维的活干完

本方案回答四个问题：在什么约束下工作、靠什么保证"不会越界"、怎么让结论可信、出事之后怎么查。 其余细节（需求条目、模块实现）分别见 PRD 与 开发设计。

01约束：这不只是一个技术选型问题

产品的形态是被下面五条约束推出来的，不是先有想法再补理由：

约束对设计的直接影响
生产环境，故障代价高宁可漏答不可错答：所有结论必须带证据（日志路径 + 行号 / 事件 ID），事实与推断必须分开写。
生产环境，等保合规口径模型不能有执行面。审计必须可用于事后追责，因此需要防篡改的日志，而不只是"有日志"。
内网无外网出口模型端点要可替换（OpenAI 兼容），升级/查版本这类"顺手联网"必须关掉；必须支持离线包部署。
麒麟最小化安装，没有 python3安装与界面补丁链路全部用 Node 实现；脚本必须 dash 兼容（麒麟的 /bin/sh 就是 dash）。
使用者是值班运维，不是安全专家界面只留必要入口；回答有固定格式；不确定时要说"还需要什么"，而不是长篇分析。

02三条设计主张

主张一：安全靠白名单，不靠提示词

让模型"不要执行命令"写在提示词里是没用的——提示词可以被绕过、被注入、被模型自己忽略。 真正的约束必须落在工具面上：模型能看见哪些工具、能调用哪些工具，由运行时的 restrict({allow}) 与 guard() 决定，与模型想不想无关。提示词只负责"让它在允许的范围里把话说明白"。

主张二：证据先于结论

每条结论必须能追溯到具体证据：日志文件 + 行号 + 原文摘录，或事件 ID。规则库里的每条故障模式都带 "识别特征 → 首查命令 → 常见根因 → 处置步骤 → 验收标准"五段，缺任何一段都不算一条合格规则。

主张三：能力要能被审计，而不只是被记录

审计日志谁都能改。所以每条审计记录带 prevHash 串成哈希链，改任何一条都会断链。 链上还带算法版本号，使得算法升级时历史链不会集体失效——审计链一旦报假警，就再也没人信它。

04一次查询的全链路

插件加载
apply(ctx) 建数据目录（0700）、建 store 与 audit、注册 25 个工具、注入两段提示词。
收窄工具面
等 agent/created 事件拿到 agent.ctx（真正的 agent scope），在其上 restrict({allow})；同时用微任务回填已存在的 agent。
执行拦截
ctx.tools.guard() 在 plain context 上注册，对所有工具调用做单调校验：不在白名单直接返回拒绝理由。
工具执行
工具内部只走文件读取（唯一例外 journal_query 用 execFile 数组传参 + 参数白名单）。
审计留痕
runQuery() 统一包装：把证据引用（日志路径 / 事件 ID）写进审计，再从返回值里剔除 refs，避免模型看到未声明的输出字段。
渲染与作答
每个工具自带 output.render()，把结构化结果转成人可读的几行文本；模型基于这些文本按固定格式出结论。
第 2 步是整个产品的命门 restrict 强制要求 agent scope：在插件 apply 的 plain context 上调用必然抛错。 早期版本把这次调用包在 try/catch 里，错误被吞掉，于是白名单从未生效—— 模型实际可见 19 个工具（含 bash、写文件、子代理）。修复方式与实测证据见 开发设计 D1。

05工具面：25 个工具怎么分工

白名单来自 lib/index.js 的 ALLOWED_TOOLS，不多一个也不少一个：23 个自有 + 2 个框架自带的联网工具。

组数量工具与职责
日志诊断（核心）3diagnose_logs 首选入口 · ls_logs 日志地图 · read_log 读片段（路径必须在 ls_logs 清单内）
知识库2kb_lookup 五层检索 · kb_note 沉淀记忆（只写 memory/，只追加）
资源与进程3sys_metrics 负载/内存/磁盘/inode · proc_list TOP · proc_detail fd/limits/cgroup
网络与服务2net_status TCP 状态与监听端口 · svc_status unit 与开机启用态
变更与完整性4recent_changes 近 N 小时配置/包变更 · pkg_history · file_hash sha256 · cert_check 证书有效期
配置与基线2config_read 白名单内配置（默认只给生效行） · sec_baseline 口令/SSH/sudo/暴露面/SUID
系统日志与出口2journal_query systemd journal · send_report 邮件（收件人必须命中白名单）
多源事件5query_ansible / query_edr / query_all / correlate / explain_events
联网核对2web_search / web_fetch（框架自带，只发查询词）

零子进程是硬指标

25 个工具里只有 journal_query 需要调外部程序（journalctl）。它用 execFile 数组传参、unit 名正则白名单（只允许字母数字与 @ . _ : -）、 并拒绝任何以 - 开头的值，杜绝参数注入。其余 24 个全部走文件读取—— 从架构上就不存在命令注入面，因为根本没有命令。

06安全模型：四层防线，缺一不可

四层不是"越多越保险"的堆叠，而是每层负责一个前一层管不到的面。实测结论：去掉任何一层都会漏。

层机制作用与不管什么
1 主restrict({allow})（agent scope）把模型可见工具收敛到 25 个。按框架设计只过滤继承层，管不到 agent 自己层注册的工具。
2guard() 单调守卫（plain context）管执行。own-layer 工具绕过 restrict，但绕不过 guard。实测拒绝信息：soc-agent 只读策略：禁止调用工具「subagent」。
3沙箱锁死mode: read-only + approval: never；权限预设表只留 soc-readonly，workspace-write / danger-full-access 从表里删除。
4插件禁用（cordis）bash / pwsh / fs / fs-search / subagent 系 / workflow / goal / skill / plugin-manager / mcp 全部不加载。

界面也是攻击面

命令表、权限档位、更新检查这些"交互入口"，本质上都是能力入口：/context 会摊开系统提示词， /preset 能切到带 bash 的模式，/update 会走 npm registry（外网出口）。 所以界面不是美化对象，而是安全边界的一部分：

位置处理
命令表63 → 8 个：help / exit / quit / q / model / status / lang / theme
启动页入口只返回「帮助」，摘掉会话与工作区、设置、有新版本、后台任务、投喂 Star
底部参数行不渲染 preset / permission 两段（配置已钉死，显示只会误导）
权限档位只剩 soc-readonly，Shift+Tab 没有别的档可切
更新检查checkForTuiUpdate() 直接返回空，不联网
品牌与文档入口启动页与侧栏换成产品自有标识（含仓库地址），不暴露框架身份
升级会静默冲掉这些封禁 dsh-tui 一升级，被改过的文件被整体替换，封禁失效但不报错。 所以升级必须走 tools/upgrade.sh（备份 → 升级 → 强制重打补丁 → 四项验证）， 且启动自检把"补丁完整 + 命令数 = 8"列为阻断级检查项。

07审计：让"事后能查"变成"改不了"

每次工具调用落一条记录到 ~/.dsh/soc-agent/audit/audit-YYYY-MM-DD.jsonl，权限 0600，只追加。

{
  "ts": 1761081600000,
  "question": "[tool:diagnose_logs] {\"since_hours\":24}",
  "toolCalls": [{ "tool": "diagnose_logs", "args": {...}, "eventIds": ["/var/log/nginx/error.log"], "at": 1761081600000 }],
  "referencedEventIds": ["/var/log/nginx/error.log"],
  "prevHash": "8f2c…a1",     // 上一条的 sha256，首条为 "genesis"
  "alg": "v2",               // 算法版本，verify 按记录自身版本重算
  "hash": "b73e…9f"
}
  • 防篡改：改任何字段（含嵌套的 toolCalls.args、referencedEventIds）都会断链。
  • 跨天续链：新文件的第一条会回溯最近一个非空日的末条 hash，不会误报断链。
  • 算法可升级：每条自带 alg，历史链用旧算法校验，不因升级集体失效。
  • 写失败必须告警：审计写失败不阻断诊断，但会在日志里显式 warn——"全程可审计"是产品承诺，断了必须让人知道。

08知识库：五层，替代"把全文塞进提示词"

层目录/文件内容
纪律knowledge/AGENTS.md行为规范与红线（先查再答、事实/推断分离、收尾必给下一步）
专家experts/linux-ops.md · network.md按领域的排查经验
技能skills/诊断操作手册.md标准手法（先看什么、再看什么）
知识kb/常见故障速查.md速查表：症状 → 首查 → 处置
记忆memory/本机基线.md本机基线与历史诊断结论（部署后填一次，之后由 kb_note 追加）

模型通过 kb_lookup 按需检索，不把全文背进提示词——提示词越长，模型越容易忽略真正的硬约束。 记忆层是唯一可写的层，且必须先征得用户同意才写，这既是纪律也是防止"自我强化错误结论"的设计。

09巡检：有故障告警，无故障也日报

任务频率行为
soc-patrol-alert每 30 分钟只在命中阈值以上故障时发信，健康时静默
soc-patrol-daily每天 08:00无论有无故障都发日报（可关）
soc-logmanage每周日 03:30压缩大日志（只压不删，可 gunzip 还原）

巡检走 bin/patrol.js，复用同一套规则库与模板渲染，不经过模型—— 定时任务不该依赖模型可用性。邮件出口有两道硬门槛：环境变量白名单 SOC_MAIL_ALLOWLIST（不配 = 全拒）+ patrol.json 的 recipients 必须同时命中。

systemd 用户级 timer 默认「登录才跑」 服务器场景需 sudo loginctl enable-linger <用户>，否则巡检会静默停止。 启动自检会检查 linger 状态并给出警告。

10部署形态：三档，按目标机的网络情况选

包体积适用场景
基础包 soc-agent-<ver>.tar.gz约 1 MB已装 dsh，且能访问 npm 源
离线包 …-offline-<os>-<arch>25–90 MB已装 dsh，不能访问 npm 源（内网常态）
dsh 全局包约 500 MB目标机连 dsh 都没装（全新内网机器）

离线包内含原生二进制（@img/sharp-<platform>、libvips 的 .so）， 必须在与目标环境相同的 OS + 架构上生成；install-offline.sh 会先校验平台匹配，不匹配直接拒绝。
