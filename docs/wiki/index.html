小安 soc-agent

部署在生产服务器上的安全运维智能体。运维用一句话描述现象，它自己读本机日志、匹配内置规则、 必要时联网核对报错含义，然后给出问题清单 · 根因 · 处置措施 · 验收方法。

一句话说清它的边界 它有 25 个只读工具，没有任何命令执行能力。不改配置、不重启服务、不写业务文件。 这不是"还没来得及做"，而是整份设计的前提——它决定了这个产品的安全定级、审计口径和界面形态。

01为什么"不给执行权"是产品能力，而不是缺陷

运维场景里，AI 助手最容易犯的错不是"答得不准"，而是答得不准还动手了。 生产环境上一次错误的 systemctl restart 或者一条误删的 rm， 代价远高于"我自己看着办"。所以这个产品把能力边界切在了一个非常具体的位置：

它做它不做
读本机日志（含轮转与 gzip）
匹配 21 类故障模式，给措施与验收
采集资源 / 进程 / 网络 / 服务 / 基线
查 journal、查配置变更、算文件哈希
联网核对报错含义（只发查询词）
把报告发到白名单邮箱
定时巡检：有故障告警，无故障日报 		执行任何命令（无 bash / 无 shell）
改配置、重启服务、杀进程
写业务文件、上传下载
派生子代理、装插件、连 MCP
向任意地址发送内容
回答与本机运维无关的问题

代价是真实的：有些证据它拿不到。服务运行态、SMART、部分内核指标只能靠命令取得。 产品对此的处理不是"猜一把"，而是给一个采集脚本，让人跑完把输出贴回来： 

# 纯只读，输出带 === SECTION: xxx === 分段，约 22 段
sh <soc-agent 安装目录>/bin/collect.sh > evidence.txt

模型拿到贴回的文本后，只允许引用真的出现了的段；某段标 [skipped: …] 就按"该维度未覆盖"处理。 这条约束写进了身份提示词，也写进了 knowledge/AGENTS.md 的纪律层。

02一次诊断长什么样

摸清现场
不知道日志在哪 → ls_logs 拿日志地图；有大致方向 → 直接 diagnose_logs。
匹配规则
diagnose_logs 扫最近改动过的日志，跑 21 类故障规则，返回带行号证据的问题清单。
补上下文
命中后用 read_log 读出问题前后若干行，确认不是断章取义；路径必须来自 ls_logs，否则拒绝。
查标准手法
kb_lookup 检索纪律层 / 专家层 / 技能层 / 速查 / 本机记忆五层知识库。
查外部知识
报错代码不认识、怀疑已知缺陷 → web_search / web_fetch，只发查询词不发日志原文。
出结论
按固定格式回答：一句话结论 → 问题清单（现象/证据/根因/措施/验收）→ 还需要什么。
落审计
每一次工具调用都写进 audit-YYYY-MM-DD.jsonl，带 sha256 哈希链，事后可逐条校验。

03三分钟跑起来

它是 dsh 的插件，依赖顺序不能颠倒：Node ≥ 18 → dsh → dsh-tui → soc-agent。

# 装到 dsh-tui profile（默认）
./install.sh dsh-tui

# 配内网模型端点（OpenAI 兼容）
export SOC_LLM_BASE_URL="http://<内网模型地址>/v1"
export SOC_LLM_API_KEY="<key>"

# 自检 → 进界面
soc --check
soc

进去直接说人话：「这台服务器有什么问题」「磁盘满了怎么排查」「nginx 起不来帮我看看」「昨天发版之后就这样了」。

内网部署别直接在线装 在线安装要访问 npm 源拉依赖树（约 86 MB、上百个包），生产内网通常没有外网出口。 用 tools/make-offline.sh 在与目标同平台的机器上生成离线包，再 ./install-offline.sh。 离线包含原生二进制，不能跨平台搬运。

04文档口径说明

这套 wiki 的全部数字与行为都来自代码本身，不是估算：工具数取自 lib/index.js 的 ALLOWED_TOOLS，故障模式取自 src/core/diagnose.js 的 RULES， 命令数取自补丁器写入的白名单。与旧文档有出入的地方（工具数 22 / 24 / 25 三种说法、单测条数）在 开发设计 · 技术债里逐条列出。
